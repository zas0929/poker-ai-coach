# Компактные выплаты и компилируемый цикл CFR+

24 октября 2026. Оригинальное исследовательское ядро, не переключение игрового тренера.

## Реализация

Добавлены два явных режима:

- `utility_storage='compact'`: терминальные выплаты хранятся в непрерывном
  `array('d')` формата «терминал × совместимая раскладка × игрок», без отдельного
  Python-ключа и tuple на каждую ячейку. Данные остаются float64, без квантования.
  Слой `CompactUtilities` сохраняет прежний читаемый mapping-интерфейс для
  Python-проверяющего кода и эталонных методов.
- `method='cfr_plus_native'`: оригинальный C++17 числовой цикл, загружаемый через
  стандартный `ctypes`. Плотные int32/float64-массивы передаются без повторной
  копии таблицы выплат. Подготовка индексов и буферов входит во время обучения.

Правила покера, построение дерева, диапазоны/коллизии, оценщик комбинаций и
settlement остаются в Python. C++ не выбирает новую модель игры: он выполняет
те же чередующиеся CFR+ обновления с полной заморозкой стратегии на все chance
раскладки перед обновлением одного игрока и тем же линейным усреднением.

Дерево/индексы проверяются перед рекурсией. Буферы переиспользуются только при
дереве с одним родителем. Максимальные размеры исходной модели сохранены.
В сборке нет `-ffast-math`; `-ffp-contract=off` исключает дополнительное слияние
умножения/сложения в числовом цикле. Это помогает сохранять арифметический порядок
эталона, а не заменяет проверку эквивалентности на каждой платформе.

Исходники C++ написаны для этого проекта; сторонние исходники солвера не включены.
Новых Python-зависимостей нет. Прежние словарное хранение и Python-методы остались
по умолчанию. Native-метод требует явно созданного компактного хранилища.

## Явная сборка и запуск

Из корня репозитория:

```bash
PYTHONPATH=backend backend/.venv/bin/python backend/research/build_native.py
PYTHONPATH=backend backend/.venv/bin/python backend/research/custom_river.py --players 2 3 --iterations 200 --method cfr_plus_native --utility-storage compact
```

Сборщик использует установленный `clang++` или `g++`; ничего не скачивает и не
устанавливает. Библиотека и JSON-манифест сохраняются в системную временную папку
в каталоге с хешем исходника и архитектурой Python. Бинарник не входит в Git.

На этой машине Python работает как x86_64 под Rosetta, поэтому macOS-сборка
явно получила `-arch x86_64`, а не архитектуру Apple Silicon по умолчанию.
В манифест записаны хеши исходника/библиотеки, флаги, компилятор и ABI. Runtime
проверяет соответствие манифеста и ABI перед вызовом. Нет автоматической
компиляции при анализе и нет незаметного fallback на Python при отсутствии
библиотеки. Ошибка требует явной сборки/пересборки. Для своего пути библиотеки
можно задать `POKER_RESEARCH_NATIVE_LIB`, сохранив соответствующий JSON-манифест.

Измерен локальный macOS/x86_64 вариант с Apple clang. В сборщике предусмотрена
Linux shared-library ветка, но эти данные не являются проверкой Linux/Render.
Сервисный деплой и упаковка компилятора остаются отдельным этапом.

В Python:

```python
game = RiverGame(board, ranges, utility_storage='compact')
policy = game.train(100, method='cfr_plus_native')
metrics = game.measure(policy)  # прежний Python-проверяющий код
```

Публичный офлайн-вход поддерживает тот же явный выбор:

```bash
PYTHONPATH=backend backend/.venv/bin/python backend/research/river_snapshot.py /tmp/snapshot.json --selected-hands /tmp/hands.json --utility-storage compact --method cfr_plus_native --bet-sizes 10 --iterations 200
```

Начало ривера и явно выбранные публичные руки по-прежнему обязательны.

## Парное сравнение с Python-эталоном

10 прежних фиксированных задач, 100 итераций, отдельный свежий процесс на метод,
последовательный запуск, чередование порядка. Эталон — индексированный Python с
исходным dict-хранилищем; новый вариант — C++ с compact. Из обоих выгружены все
вероятности, ключи информационных множеств и результаты лучших ответов.

На всех 10 задачах разность вероятностей, payoffs, лучших ответов и gains —
**0** в выполненном прогоне. Оба метода прошли прежний порог качества 0.5% банка.
Это проверка сохранения результата эталона в заданной модели, не сертификат GTO
полного покера и не новая гарантия сходимости для 3+ игроков.

примерно в 11–14 раз; на малых двухсторонних выигрыш всего запуска гораздо меньше.

При 100 итерациях порог качества прошли **12/13**. `flush_6` с разрывом 0.607%
не объявлен успешным. Дополнительный запуск **только этой задачи** на 200
итерациях дал 0.2501% банка за 4.12 секунды, около 38 МиБ. Это отдельный бюджет,
а не утверждение «все 13 прошли на 100 итерациях».

4.76 секунды на построение, 4.65 на обучение и 6.63 на Python-проверку лучших
ответов: ускорение одного цикла не отменяет остальные затраты.

## Проверки реализации

Проверены все выплаты compact против dict, политики и лучшие ответы для 2–6
мест, шесть действий в узле, взвешенные коллизии, расширенные сочетания до
4096, сфолдившие вклады, побочные банки, повторные короткие рейзы, живые решения
с нечётной фишкой, терминальный олл-ин и повторный вызов native-обучения.
Отсутствующая/устаревшая библиотека или манифест не запускают fallback.

```bash
PYTHONPATH=backend backend/.venv/bin/python backend/research/benchmark_native.py --check
PYTHONPATH=backend backend/.venv/bin/python backend/research/benchmark_expanded.py --method cfr_plus_native --utility-storage compact
PYTHONPATH=backend backend/.venv/bin/python backend/research/benchmark_expanded.py --method cfr_plus_native --utility-storage compact --iterations 200 --cases flush_6
PYTHONPATH=backend backend/.venv/bin/python -m unittest discover -s backend/tests -p test_native_cfr.py
```

Native-тесты явно собирают временную библиотеку, если её нет и доступен локальный
компилятор; без компилятора помечаются пропущенными. Это отличается от runtime,
который никогда не компилирует автоматически.

## Границы и следующий этап

Не изменены лимит 64 по умолчанию, максимальное число узлов и абстракция ставок.
Полные диапазоны на 1–5 оппонентов, будущие улицы и card bunching не реализованы.
Нет подключения к боевой подсказке, LLM, подписке или серверному native-деплою.

Следующий этап — восстановление уже начавшейся торговли ривера из публичной
истории: текущие вклады, очередь, последний полный рейз и права на повышение.
Это позволит готовить настоящую точку решения внутри раздачи, сохранив явные
границы диапазонов и проверку качества. Широкий обучающий набор и дальнейшее
снижение стоимости проверки остаются отдельными задачами.


Этап восстановления публичной торговли ривера выполнен отдельно; native-цикл
работает с непустым фиксированным префиксом без изменения ядра.
[Проверки и границы](SOLVER_RIVER_CONTINUATION.md).
