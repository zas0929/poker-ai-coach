# Ограниченный теневой исполнитель

24 октября 2026. `research.shadow_executor.ShadowExecutor` — локальный
исследовательский исполнитель. Игровые маршруты, подсказки, UI и хостинг
не изменены; фоновые сервисы Render/Redis не создавались.

## Как работает очередь

Один поток-координатор вызывает контракт анализа. Численный расчёт по-прежнему
идёт в отдельном дочернем процессе под монитором времени/RSS. `submit` проверяет
и копирует публичный запрос, ставит задачу в очередь и возвращает квитанцию;
он не ждёт окончания анализа. `poll` также возвращает текущий результат сразу.
Сериализация/хеширование входа синхронны, поэтому это не обещание нулевой
задержки постановки большого снимка.

Ограничения по умолчанию:

- один активный расчёт и два ожидающих;
- до 128 квитанций с результатами и привязанных контекстов;
- журнал из последних 256 событий;
- прежние индивидуальные бюджеты `ResearchLimits` для каждого дочернего процесса.

`queue_full` и `capacity_rejected` возвращаются явно; очередь сама не растёт.
При исчерпании памяти квитанций сначала удаляется самая старая завершённая.
Если все ещё выполняются, новый получатель отклоняется. Удалённая квитанция
при опросе получает `expired`. Число контекстов ограничено тем же хранением.
Общий лимит RSS родительского приложения здесь не реализован: бюджет контракта
относится к процессу расчёта, а не к приложению вместе с очередью.

## Дедупликация и независимые получатели

Идентичность задачи включает полный хеш запроса, пробную руку, параметры дерева,
бюджеты и отпечаток версии движка. Одинаковые **незавершённые** запросы получают
общий `job_id`; разные контексты — отдельные `ticket_id`. Повтор того же запроса
в том же контексте возвращает ту же квитанцию со статусом `reused`.

Контекст — заданный вызывающим кодом канал результата, например локальный
тренер конкретной сессии. Его идентификатор не является id задачи или руки.
В журнале он заменяется SHA-256; длина исходной строки ограничена 256 символами.

Изменённый запрос в том же контексте заменяет предыдущий, даже если публичный
ключ остался тем же, но изменилась рука/настройка. Прежняя квитанция становится
`stale`. Готовые результаты не кэшируются для новых запросов: после завершения
повтор запускает новую задачу. Исходный запрос копируется до постановки;
последующие изменения объекта вызывающим кодом не меняют работу в очереди.
Возвращаемые результаты и журнал также копируются.

## Устаревание и отмена

`advance(context_id, latest_public_key)` сообщает о смене решения. Исполнитель
сам не подписан на комнату и не знает, что игрок уже походил. Смену ключа должен
передать будущий вызывающий код.

При смене решения кандидат удаляется, включая уже готовый результат. Если
общую задачу ещё ждёт другой контекст, расчёт для него продолжается. Когда
получателей не остаётся:

- ожидающая задача физически удаляется из очереди и никогда не запускается;
- активная получает сигнал отмены; монитор завершает дочерний процесс и ждёт
  его выхода через `kill`/`wait`;
- частичный результат не получает допуск и не возвращает готовую стратегию.

`cancel(ticket_id)` отменяет только указанного получателя. Статус квитанции
меняется сразу, физическая остановка процесса происходит кооперативно на
следующем шаге монитора. `stats()['jobs'] == 0` после отмены означает, что
исполнитель закончил обработку и дождался дочернего процесса.

Возврат контекста к прежнему публичному ключу не оживляет старую задачу:
проверяется актуальная квитанция, а отменённая работа удалена из дедупликации.
Устаревший результат не может перезаписать результат нового запроса.

## Состояния квитанции и анализа

Квитанция имеет `queued`, `running`, `completed`, `stale`, `cancelled`, `error`
или `expired`. **`completed` означает завершение, а не допуск:** внутри может
находиться `quality_rejected`, `unavailable` или другой отказ контракта.
Для пригодности анализа проверяются `result.status` и `result.admission`.

Контракт теперь поддерживает `cancel_event` и статус `cancelled` с кодом
`ANALYSIS_CANCELLED`. Во всех ветках `live_advice_allowed` остаётся `false`,
а инструкция сохранить текущий совет — `true`. Ошибка одного расчёта не
останавливает обработку следующих задач. Неверная версия, идентичность,
несогласованный статус или неполный результат анализатора дают
`SHADOW_WORKER_FAILED`, без публикации частичного кандидата.

## Журнал и завершение

Журнал содержит id задач/квитанций, публичные ключи, хеши контекстов, этапы,
причины допуска/отказа, ожидание в очереди и общее время получателя. В нём нет
пробных карт, диапазонов, исходных контекстов или текстов исключений.
Это ограниченный журнал в памяти; дисковый аудит и восстановление после
перезапуска пока не реализованы.

`close()` запрещает новые запросы, отменяет ожидающие и активные задачи,
завершает поток и ждёт его выхода. Готовые квитанции остаются доступными
в пределах лимита хранения. Поток не daemon; исполнитель нужно закрывать.
`close(wait=False)` только инициирует остановку, а не гарантирует, что поток
и дочерний процесс уже завершены.

Не следует создавать исполнитель через `with` внутри обработчика каждого
игрового действия: выход из контекста вызывает ожидающее завершение `close()`.
Будущий исполнитель живёт отдельно от обработки ходов и закрывается при
остановке приложения.

```python
executor = ShadowExecutor(max_pending=2)  # отдельный жизненный цикл
receipt = executor.submit("trainer:local-session", public_research_request)
# Текущая подсказка тренера остаётся доступной.
# Позже, при изменении решения:
executor.advance("trainer:local-session", latest_public_key)
# При отдельном опросе результата:
state = executor.poll(receipt["ticket_id"])
# При завершении исследования/приложения:
executor.close()
```

Время ожидания в очереди отделено от `result.timing.wall_seconds`. Бюджет
контракта начинается при запуске расчёта; общий срок от постановки до выдачи
может быть длиннее. Проверка актуальности обязательна независимо от бюджета.

## Контрольные прогоны

[Отчёт реальных процессов](research/river-shadow-executor-2026-10-24.json)
содержит версию и отпечаток исполнителя, результаты и журнал. Все три группы
проверок прошли:

1. Два контекста разделили один native-расчёт; первый стал `stale`, второй получил
   `ready`. Физически запущена одна задача.
2. При активном шестиместном расчёте одна задача ожидала, следующая получила
   `queue_full`. Ожидающая удалена, активная отменена в фазе `build`, процесс
   завершён и собран. В контрольном замере отмена заняла около 0,24 с.
3. Следующая задача получила `ready`; смена её контекста после выдачи убрала
   готового кандидата. Закрытие оставило ноль активных/ожидающих задач.

Описанное время остановки — наблюдение на локальной машине, не жёсткий SLA.
Монитор RSS/времени остаётся мягким, с опросом примерно раз в 0,2 с.
Юнит-тесты с управляемым анализатором проверяют возврат из постановки до конца
расчёта, переполнение, ёмкость хранения, приватность журнала, исключения,
закрытие и гонку возврата к старому ключу.

```bash
PYTHONPATH=backend backend/.venv/bin/python backend/research/build_native.py
PYTHONPATH=backend backend/.venv/bin/python -m research.benchmark_shadow
PYTHONPATH=backend backend/.venv/bin/python -m unittest discover -s backend/tests -p test_shadow_executor.py
```

Предыдущие отчёты контракта фиксируют отпечатки прежней версии исходников;
новый отчёт содержит версию с отменой. Переписывать исторические замеры при
изменении координатора не требуется.

## Следующий шаг

Можно готовить локальное подключение к режиму тренера под выключенным по
умолчанию флагом: постановка публичного снимка отдельно от ответа на ход,
передача актуального ключа и сбор сравнений в журнал. До этого нужен явный
выбор исследовательских диапазонов и размеров: исполнитель сам не обрезает
полные диапазоны и не подставляет известные карты соперников. Разрешение
заменять советы, серверный деплой native-ядра и новые расходы здесь не включены.
