# Упаковка ограниченного разбора для staging

Сервис: `poker-ai-coach-api`, workspace `poker-ai-coach`, прежний бесплатный
Render web service. Контекст сборки — `backend/`, Dockerfile — `backend/Dockerfile`.
Новые сервисы, платные планы и базы данных не создаются.

## Образ

- В отдельной стадии компилируется существующий C++17 native-код для платформы
  деплоя. Библиотека и её манифест попадают в `/opt/poker/native/`.
- Runtime содержит `app/`, `research/`, `libstdc++6` и `procps` для наблюдения RSS.
  Компилятор в runtime не копируется; запрос не запускает сборку.
- Последний шаг сборки `python -m research.verify_packaged` проверяет ABI,
  флаги, SHA исходника/бинарника, затем все пять моделей через настоящий
  изолированный процесс, проверку качества и EV. База и секреты ему не нужны.
- Сохраняется один uvicorn worker. Очередь решателя имеет одного владельца;
  ограничения — 300 итераций, 10 секунд, 128 MiB наблюдаемой RSS, две ожидающие
  задачи, 64 комбинации и 4000 узлов. RSS — наблюдаемый мягкий предел, не cgroup.
- `.dockerignore` допускает только нужные исходники, исключает локальные базы,
  `.env`, Python-кэш и локальные платформенные бинарники.

## Включение

В Render с сохранением остальных переменных:

```text
POKER_RIVER_LESSONS_ENABLED=1
POKER_RESEARCH_NATIVE_LIB=/opt/poker/native/libpoker_cfr.so
```

Старый `POKER_LOCAL_RIVER_LESSONS=1` продолжает работать для локального запуска.
Новый флаг имеет приоритет: явный `0` выключает функцию, даже если старый равен `1`.
По умолчанию функция выключена и research-модули не импортируются приложением.
При включении библиотека проверяется **до** создания очереди. Отсутствующий или
несовместимый бинарник оставляет режим недоступным, основной сервер продолжает
обслуживать игру; каталог сообщает `LESSON_ENGINE_UNAVAILABLE`.

После выкладки требуется проверить именно новый commit и статус `live`, затем
каталог с `enabled: true`, закрытые операции без профиля (401), примеры и собственные
задачи через Bearer-токен. Отдельная проверка — сохранённые завершённые решения
на staging. Деплой с рабочим HTTP-портом сам по себе этого не подтверждает.

База остаётся существующей Supabase private схемой. В ней индекс завершения
создаётся идемпотентно; старые решения без отметки завершения не импортируются.
Задачи расчёта хранятся в памяти и после перезапуска требуют повторного запуска.
Бесплатный сервер может засыпать; холодный старт не считается скоростью солвера.

## Подтверждённая выкладка — 25 октября 2026

Развёрнут commit `cc31a2813727f9b840e5da4e1ff0f09569f38bbb`,
deploy `dep-dberaojrjlhs738kq2l0`, статус `live`.
[Экран разбора истории](https://poker-ai-coach-eight.vercel.app/practice/river/history),
[учебные примеры](https://poker-ai-coach-eight.vercel.app/practice/river).

Сборочный лог Render подтверждает `native_kernel: verified` и `ready` для всех
пяти моделей. По HTTPS проверены все пять моделей и завершённое решение
на новых одноразовых учебных профилях; чужие задачи/решения недоступны.
Полный запрос примера в этом прогоне занял 5,6–10,2 секунды, включая сеть,
аутентификацию, очередь и polling; это не чистое время native-обучения.
Frontend отдаёт страницу истории с HTTP 200 и содержит правильный URL API.
[Отчёт приёмки](research/river-staging-2026-10-25.json).

Повторить ограниченную приёмку:

```bash
PYTHONPATH=backend backend/.venv/bin/python backend/tests/river_staging_smoke.py --url https://poker-ai-coach-api.onrender.com
```

Скрипт допускает только именованный staging API и отдельный локальный preview,
создаёт свои тестовые профили, не обращается к существующим пользователям или
комнатам. Если системный Python на macOS не настроил CA-сертификаты, следует
указать доверенное хранилище через `SSL_CERT_FILE`; проверка TLS не отключается.
Прокси Render добавляет отдельное поле `Vary: Accept-Encoding`, поэтому проверка
объединяет все поля `Vary`, сохраняя `Authorization, Origin` от приложения.

Backend-пакет прошёл полный прогон 442 тестов (3 пропущены без отдельной
PostgreSQL БД); после доработки staging-проверки прошли ещё её 5 целевых тестов.
Локальный Docker daemon был недоступен из-за блокировки Mac; контейнерная
сборка и проверка выполнены на настоящем Linux builder Render.

Обновление двух не секретных переменных через Render MCP запустило выкладку
нового commit. Перед этим git push сам не обновлял сервис, несмотря на отображаемое
`autoDeploy: yes`: предыдущая live-версия была от 23 октября. Последующие выкладки
также нужно подтверждать конкретным live commit, а не наличием кода в `main`.
Документационные и тестовые поправки после этой приёмки не меняют runtime образа.

подписки на общую задачу, кэширование, снятие результата после хода
и отказ старой версии позиции (409). Чтение состояния во время расчёта
заняло 0,17–0,23 с. Полный тест позиции занял 9,8–19,0 с, включая сеть,
проверки кэша и отмены; это не время чистого native-расчёта.

Повторить проверку текущего хода:
